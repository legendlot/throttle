## 1. Why this exists, and what it is not

LOT is onboarding **LimeChat** as an AI voice-bot engine. The first use is COD confirmation calls,
replacing calls a CS agent makes by hand today. The bot confirms, cancels, or converts the order on the
call; every unresolved call — no answer, busy, dropped, "needs a human" — still needs a WhatsApp
follow-up, which is Relay's job.

Pruthvi asked for *"an API for Relay… to capture the call outcomes and transcripts generated by the AI
voice bot during **abandonment calls** and any future voice campaigns."* ⚠️ **His words say abandonment
calls; the business framing given to this session was COD confirmation.** They are different populations
with different triggers. This spec assumes **both**, because the channel abstraction below does not care
which — but the first flow to build must be named explicitly before anyone starts.

**This is not "an integration with LimeChat."** Afshaan, 2026-09-02:

> *"Relay absolutely owns the decision to contact a customer or not. It's not LimeChat's customer. They
> cannot make a call by themselves. We will have to orchestrate all of that."*

> *"I don't want my agents to go through five different systems… I would want to integrate as much as
> possible but still use their engine."*

So this is **a new Relay channel — voice — that happens to have LimeChat as its first adapter**, exactly
as SMS/RCS has TrustSignal and email has Resend. That framing is the whole design. It is also what makes
the cost defensible: ~1.5 of the ~10–12 days is LimeChat-specific; the rest is channel work that a second
voice vendor would reuse for free.

### 1.1 Scope — voice engine only (Afshaan, 2026-09-02)

⛔ **We are taking their voice engine and nothing else.** LOT owns its WABA and will keep sending its own
WhatsApp messages, so: **no LimeChat WhatsApp inbox, no WhatsApp Calling, no LimeChat helpdesk/ticketing.**
Their calls run on telephony (Exotel or Knowlarity). This removes the WABA-conflict risk in §3.4 by
decision rather than by mitigation, and keeps CS on Pitstop.

### 1.2 Trigger ownership — the end state, and the deliberate interim

The **end state** is that every trigger originates in Relay: it decides who gets contacted, the send gate
(suppression → consent → freq cap → quiet hours → exclusions) applies to voice as it does to every other
channel, and LimeChat executes. That is the whole point of §4.

⭐ **But Phase 0 deliberately does not do that** (Afshaan, 2026-09-02):

> *"I want to do it in the least disruptive manner. If that means that LimeChat fires directly from
> Shopflo triggers and whatnot, and we have to use the two surfaces for a few days, that is perfectly
> fine — as long as we are able to capture all the details that we need for a final integration."*

So LimeChat may trigger off its own native Shopflo integration to begin with. **The single condition is
total capture:** every call and every outcome must reach `comms.voice_calls`, including calls Relay did
not ask for, so nothing is lost before the trigger moves. A `voice_calls` row must therefore tolerate a
NULL `campaign_id`/`journey_id`/`enrolment_id` and an `origin` of `vendor_triggered`.

⚠️ **Two consequences of Phase 0 to accept knowingly, not discover later.** (a) The send gate does not
apply to vendor-triggered calls — suppression, frequency cap and quiet hours are LimeChat's behaviour, not
ours, for that window. (b) The live C2P journey keeps running, so a COD order can receive **both** a bot
call and the C2P WhatsApp ask (§7). Both are time-boxed by choice; neither is a defect.

⚠️ **Open, and Afshaan's to answer:** does LimeChat integrate with Shopflo directly for the trigger, or
does Relay sit in between from day one? Phase 0 assumes direct. See §11 Q13.

## 3. What already exists — theirs

Measured from LimeChat's own documentation, 2026-09-02. **Both directions are configuration on their
side. LimeChat builds nothing.**

### 3.1 Relay → LimeChat (we decide who gets called)

Custom Events API:

```
POST https://flow-builder.limechat.ai/api/v1/cvf-events
Content-Type: application/json
x-limechat-uat:  <access token>      # profile settings
x-fb-account-id: <account id>        # account settings

{ "distinct_id": "<our profile ref>",
  "phone": "+91XXXXXXXXXX",
  "event": "lot_cod_confirm_requested",
  "data": { "order_id": "...", "order_value": ..., "items": "...", ... } }
```

At least one of `distinct_id` / `phone` is required. `data` is arbitrary key-value. The event starts a
LimeChat flow. **This is the entire outbound contract.**

### 3.2 LimeChat → Relay (outcomes come back)

Their **API Action** node is a full HTTP client usable inside a flow: GET/POST/PUT/PATCH/DELETE ·
**Bearer Token** / Basic / API Key / none · custom headers, query params, raw or form-encoded body ·
`{{variable}}` templating · cURL import · built-in connection test · **parses the response back into
flow variables**. Bearer matches our existing token pattern exactly, so they POST to our route directly.

### 3.3 The call nodes — already purpose-built for this

`COD Order Verification Call`, `COD to Prepaid Conversion Call`, `Abandoned Checkout Phone Call`,
`Reorder Call`, `Start Telephony Call`, `Start Telephony Call (Async)`, `Start WhatsApp Call`.

**COD Order Verification Call** — inputs: Order ID, Item Names, Order Value, Voice Agent, Customer Name,
CRM Inbox, Custom Prompt, Discount Percent, **Allow Cancellation** (default false), Confirmation Tags,
Cancellation Tags. Outputs, verbatim:

| Output | Type | Values |
|---|---|---|
| `successful` | bool | |
| `call_id` | text | |
| `call_status` | text | **`completed`, `failed`, `busy`, `unanswered`** |
| `user_confirmed` | bool | |
| `user_requested_handoff` | bool | |
| `call_summary` | text | |
| `cod_verification_call` | object | |

**Start Telephony Call (Async)** — outputs `successful`, `call_id`, `call_status`
(**`initiated`, `completed`, `failed`**), `call_summary`, **`call_transcription`** (full transcript).

⚠️ **Three findings that shape the build:**

1. **The COD node exposes `call_summary` but NOT `call_transcription`.** Only the generic async node
   returns a transcript. Pruthvi's transcript ask and the ready-made COD node are therefore **in
   tension** — we get one or the other unless LimeChat can combine them. Ask before designing storage.
2. **The two nodes use inconsistent `call_status` vocabularies.** Our mapping layer must normalise
   both, and this is the layer that ages worst as they add statuses. Treat their strings as
   *provider status*, never as our enum.
3. ⛔ **Async result delivery is UNDOCUMENTED.** Their docs say the flow "does NOT wait" and that
   summary/transcript/final status "may be populated after the call completes" — **without saying how
   the result is delivered**. This is the single largest unknown in the whole design and cannot be
   engineered around. It is question 1 in §11.

### 3.4 Their platform shape — two traps

- **LimeChat is a full helpdesk** (inboxes, tickets, agents, CSAT, contacts, analytics), which overlaps
  Pitstop directly. ⛔ **Use them as a voice engine only.** The call nodes carry an optional **`CRM
  Inbox`** field — **leave it unset**, because setting it pulls conversations into their console and
  fragments CS across two systems, which is exactly what Afshaan ruled out.
- ✅ **WhatsApp Calling — RULED OUT by decision, 2026-09-02 (§1.1), so the risk is closed.** For the
  record of why it would have been one: they market an "exclusive Meta partnership" and ship a
  `Start WhatsApp Call` node, and their WhatsApp inboxes run on 360Dialog / Cloud API / Sinch, while
  **LOT's WABA is already bound to commsops** — two systems on one WABA is where this would have broken
  something live. Plain telephony (their **Exotel** / **Knowlarity** inboxes) avoids the WABA entirely,
  and Exotel is already in our stack (436 rows in `store.cs_calls`). **Do not revisit WhatsApp Calling
  without re-opening the WABA question first.**
- **One irreducible exception to the single-pane goal:** the Voice Agent roster is server-fetched from
  LimeChat and the persona lives there. Relay can pass a per-call `Custom Prompt`, but agent authoring
  stays in their console. Everything else should be invisible to LOT agents.

## 4. Architecture — voice as a Relay channel

```
  comms.segments / journeys                    ← Relay decides WHO and WHEN
        │
        ▼
  send gate  (suppression → consent → freq cap → quiet hours → channel rule)
        │
        ▼
  adapters/voice.js  ──POST cvf-events──►  LimeChat flow  ──► telephony (Exotel/Knowlarity)
        │                                        │
        │                                        │ API Action node
        ▼                                        ▼
  comms.voice_calls  ◄────────────  POST /ingest (LIMECHAT_INGEST_TOKEN)
   (current state)                               │
        │                                        ▼
        └──────────────────────────►  comms.events  ── real-time ──► journey trigger
                                      (small outcome enum only)          │
                                                                         ▼
                                                          WhatsApp follow-up via C2P
```

The channel abstraction already exists (`adapters/sms.js`, `rcs.js`, `email.js` behind one send gate).
Voice slots into it. A journey step *places a call* the same way it sends a message, and exclusions,
capping, quiet hours and reporting come free rather than being rebuilt.

## 5. Data model

**Outcome → `comms.events`. Transcript → never `comms.events`.**

`comms.events` is 951,344 rows / 896 MB and its `properties` payload is **max 1,984 bytes, avg 481**. A
5–20 KB transcript is 5–20× the largest payload that has ever existed there. Worse, `getProfile` does
`select=*` on the last **50** events (`index.js:361`), so fifty transcript rows turn a ~25 KB contact
page into multiple MB.

Proposed, mirroring `bot_sessions`/`bot_session_steps` and `comms.messages`:

- **`comms.voice_calls`** — the current state of one external object.
  `id` · `connector` · `provider_call_ref` (their `call_id`, UNIQUE per connector) · `profile_id` ·
  `purpose` · `campaign_id`/`journey_id`/`enrolment_id` · `status` (**our** closed enum) ·
  `provider_status` (their raw string, never interpreted) · `reason` · `user_confirmed` ·
  `user_requested_handoff` · `requested_at`/`dialed_at`/`answered_at`/`ended_at` ·
  `duration_seconds` · `summary` · `raw jsonb`.
- **`comms.voice_call_turns`** *(only if transcripts are taken — see §11 Q6)* — append-only,
  `voice_call_id` · `seq` · `speaker` · `text` · `spoken_at`.
- **`comms.events`** gets only a small outcome row (`voice_call_completed` + a scalar outcome in
  `properties`) so journeys can trigger off it. No transcript, no summary.

**Our status enum** (proposed, closed): `requested` · `dialing` · `answered` · `no_answer` · `busy` ·
`failed` · `completed` · `cancelled_by_us`. Their `call_status` maps into it; unmapped values land in
`provider_status` and raise an `unmapped` connector alert rather than being silently coerced.

## 6. The compliance gap — this is the real blocker, and it predates any code

| Control | State today | Evidence |
|---|---|---|
| Voice consent | **Does not exist.** `comms.consent` holds exactly four channel/purpose pairs: marketing/email 154,466 · marketing/whatsapp 136,092 · transactional/email 91,308 · marketing/sms 10,611 | measured 2026-09-02 |
| Pre-send DND/DNC check | **None anywhere.** DND is *learned after the fact*, SMS-only, from TrustSignal delivery failures (`DND_STATUSES = {dnd, dndcf}`) | `adapters/sms.js:115-124,144-147` |
| Voice quiet hours | **No row.** Would silently inherit global 22:00–08:00 — **more permissive** than the SMS TCCCPR band (21:00–10:00) | `gate.js resolveQuietWindow` |
| Voice opt-out surface | None. `optout.js` STOP handling is messaging-only | `optout.js:14` |

⚠️ **Under the chosen architecture LOT places the calls, so this exposure is unambiguously ours, not
LimeChat's.** A `voice` channel row in `comms.consent`, a `voice` quiet-hours row, and a decision on the
DND basis are **prerequisites, not follow-ups**. This is not a build question and cannot be closed by a
session.

## 7. Collision with the live C2P journey

⛔ **A COD confirmation flow already exists and is live.** `COD → Prepaid (C2P)`, active since
2026-07-29, triggers on `order_placed` filtered `{"is_cod":"true"}`, sends an interactive WhatsApp
template with Make Payment (Cashfree, `(COD−50)×0.97`) / Confirm COD Order / Cancel Order, 60-minute
window. **1,050 enrolments: 642 completed, 377 no-response.** Outcomes are written as Shopify order tags
(`relay-c2p-converted`, `relay-c2p-no-response`, `relay-c2p-late-confirm`…), not to a table.

So the voice bot lands on occupied ground, and **the same COD order qualifies for both**. Journeys still
have **no exclusion machinery** — that is the decided-but-unbuilt `[relay][build][MED]` item ("bring the
same exclusion options to JOURNEYS", Afshaan decided send-time evaluation + a `skipped` reason bucket on
2026-09-02). **That item is a hard dependency of this one**, not an adjacent nicety.

Three orderings are possible and one must be chosen (§11 Q8): voice **replaces** C2P · voice runs
**before** C2P and C2P becomes the fallback for unresolved calls · they run **alongside** (rejected —
double-touch).

⭐ The follow-up half Pruthvi asked for **largely exists already**: C2P covers confirm / cancel /
convert-to-prepaid / no-response. The new work is *routing into it from a call outcome*, not new journeys.

## 8. Observability — the silence problem

If LimeChat stops pushing outcomes, nothing today notices. We cannot distinguish *no call was made* from
*the call happened and the outcome never arrived*. This is the **HP Crest failure mode**: 2026-08-21, the
campaign reported `sent` while all 5,199 SMS fallback messages died at the carrier, unnoticed for weeks.

Two defences, both cheap because the pattern is already in-house:

1. Port `sales.connector_alert_outbox` — `alert_kind ∈ stale | silent | unmapped`, drained via
   `detect_connector_alerts`. `silent` is exactly this detector.
2. **Reconcile counts, don't trust callbacks:** every call Relay *requests* writes a `voice_calls` row at
   `requested`. A row still at `requested` past a TTL is a hole, and it is visible without the vendor.

⚠️ Fix the swallowed journey-trigger errors (`ingest.js:179,196`) as part of this, or an outcome can land
and fire nothing, silently.

## 9. What NOT to do

- ⚠️ Do not let LimeChat trigger calls off Shopflo **in the end state** — Relay owns the decision (§1.2).
  **Phase 0 deliberately allows it**, time-boxed, on condition of total capture. Do not "fix" it early.
- ⛔ Do not set the `CRM Inbox` field on the call nodes (§3.4).
- ⛔ Do not put LimeChat on LOT's WABA, and do not enable WhatsApp Calling (§1.1).
- ⛔ Do not adopt their WhatsApp inbox — LOT sends its own WhatsApp from its own WABA (§1.1).
- ⛔ Do not adopt their helpdesk/ticketing — Pitstop owns inbound CS.
- ⛔ Do not store transcripts in `comms.events.properties` (§5).
- ⛔ Do not copy `sales.connector_*` wholesale: those connectors are **pull** (cursor, window,
  `rows_fetched`, schedule). LimeChat is **push**. Config + alerting transfer; run/cursor does not.
- ⛔ Do not treat their `call_status` strings as our enum (§5).
- ⛔ Do not cite "retention pruning" as an existing control — it does not exist (§10, R3).

## 10. Risks

| # | Risk | Why it bites |
|---|---|---|
| **R1** | **No voice consent basis, no pre-send DND check, no voice quiet-hours row** | §6. Regulated outbound voice, and under this architecture the exposure is LOT's. Prerequisite, not follow-up. |
| **R2** | **Transcripts silently reclassify `relay_view`** | `decisions.md` blessed full contact PII for every `relay_view` holder — *"all internal audience"* — but that call was about phones and emails. Transcripts are unbounded free text (card fragments, addresses, health/family context, complaints about named staff) riding the same ungated `getProfile` `select=*` path under one blanket `canView` (`index.js:3340`). `getEventFeed` allow-lists 6 event names precisely because it is "a PII feed, not an arbitrary event browser"; `getProfile` has no such allow-list. **Needs a fresh explicit decision from Afshaan.** |
| **R3** | **No erasure path, and transcripts void the reason we lack one** | `customers/redact` writes suppression rows and **deletes nothing**, justified in its own header comment by *"we hold no special PII store"* — false the moment a transcript lands. `customers/data_request` is a literal no-op. **Zero `gdpr_redact` suppressions have ever been written.** And there is **no retention pruning at all**: one unscheduled prune function; `cron.job` holds a single unrelated job. Transcripts would be retained indefinitely with no delete mechanism. |
| **R4** | Double-touch with live C2P | §7. Blocked on the journey-exclusions item. |
| **R5** | Silent vendor failure | §8. |
| **R6** | **First vendor-held token in an internal-only class** | Every `*_INGEST_TOKEN` is internal and self-minted (`integrations.md:435-457`). A LimeChat token is held by a third party: rotation stops being an internal lockstep exercise, and there is no scope table, expiry, revocation list or rate limit. |
| **R7** | Order-state write conflict | If the bot cancels on the call, who writes it to Shopify — them (via `Update Order Status` / Cancellation Tags) or us? Both is a conflict; neither makes the cancellation a note nobody acts on. |
| **R8** | Async delivery undocumented | §3.3(3). Blocks the inbound contract. |

## 12. Effort and phasing

| Piece | Days | Vendor-specific? |
|---|---|---|
| Outbound adapter (`adapters/voice.js` → `cvf-events`) | 0.5 | ✅ yes |
| Inbound route + `LIMECHAT_INGEST_TOKEN` + status mapping | 1 | ✅ yes |
| `comms.voice_calls` + normalising their status vocabularies | 2 | no |
| **Voice as a real channel** — consent channel, quiet-hours row, rate card, send-gate integration, journey send-step, reporting | 4–6 | no |
| Connector registry (port from `sales`) + silence detection | 2.5–3 | no |
| Vendor-facing API docs + sandbox path | 0.5–1 | ✅ yes |
| **Total** | **~10–12** | **~1.5 vendor-specific** |

⭐ **The channel is the work; the vendor is a plug.** A second voice vendor later costs ~1.5 days, not 12.

### 12.1 Phasing — least-disruptive first (Afshaan, 2026-09-02)

| Phase | Trigger | Relay's job | Ships |
|---|---|---|---|
| **0 — capture only** | **LimeChat**, off its own Shopflo integration | Receive and store every call + outcome. Nothing else changes; C2P keeps running. | Inbound route + scoped token + `comms.voice_calls` + status mapping + silence detection. **~3.5–4 days.** |
| **1 — Relay triggers** | **Relay** via `cvf-events`, behind the send gate | Owns who is called and when; voice becomes a real channel | Outbound adapter + consent channel + quiet-hours row + journey send-step + exclusions. **~5–7 days.** |
| **2 — transcripts** | unchanged | Turns table, retention, and a read gate | Only behind an explicit PII decision (R2/R3). |

⭐ **Phase 0 is the whole near-term ask and it is genuinely small.** It is also the phase that makes
Phase 1 safe: by the time Relay takes the trigger, we already hold real outcome data to model against
rather than a guess at their vocabulary.

⭐ **Build Phase 0 as if the trigger were already ours.** `origin` (`relay` | `vendor_triggered`) and a
nullable enrolment link are the only two things that let Phase 0 rows and Phase 1 rows live in one table.
Getting that wrong is the one thing in Phase 0 that would need a migration later.

⚠️ Phase 0 does **not** need the journey-exclusions item; Phase 1 does, and it should ship before or
with it (§7).

⛔ **Phase 0 does not start until Q1 is answered** — it determines the inbound contract, and it is the
one thing we cannot design around. **Q8 and Q13** shape Phase 1 and can be answered in parallel.
